The Java implementation of [XiHan Spec](https://github.com/XiHanFun/framework-spec): the primitives layer, manifests, the invocation context, the pipeline, operation contracts and the out-of-process plugin runtime. Use it to bring the same primitives as the .NET host (the reference implementation, [XiHan.Framework](https://github.com/XiHanFun/XiHan.Framework)) into JVM applications, or to write Java plugins that run in the .NET host. The spec lives in `spec/` as a submodule, and conformance is verified by the conformance vectors and the black-box runner of the spec repository.

## Modules

The whole SDK is a single Maven artifact, `com.xihanfun:xihan-framework`. Like the SDKs for other languages it is one package, with the JPMS module name `com.xihanfun.framework`, divided into Java packages:

| Java package | Contents | Spec |
| --- | --- | --- |
| `com.xihanfun.framework.primitives` | `Error` / `ErrorCode`, `Result<T>`, `Maybe<T>`, `TypedId<Tag, V>`, `LifecycleState`, `PipelineStage`, `Stability`, `BaggageKeys`, message keys and templates (`MessageTemplate`, `MessageCatalog`, `MessageScope`), `FrameworkException`, `FrameworkInfo` | RFC-0001, RFC-0010, `conventions/` |
| `com.xihanfun.framework.primitives.json` | Wire JSON encoding: the Jackson module `PrimitivesModule` | RFC-0001 (wire encoding) |
| `com.xihanfun.framework.manifest` | The `xihan.manifest.json` model, strict schema-based reading, normalized output and validation, capability declarations and requirement text | RFC-0002, `manifest/manifest.schema.json` |
| `com.xihanfun.framework.invocation` | `Context`: cancellation and deadlines (attributed by token to `KERNEL_TIMEOUT_001` / `KERNEL_CANCELLED_001`, with callback registration), W3C tracing, registered baggage, the item bag `Items`, values passed by derivation | RFC-0003 |
| `com.xihanfun.framework.pipeline` | The eleven-stage `PipelineBuilder`: `use` / `useAt` / `useNamedInstance`, `before` / `after` (type name or instance name), `describe` / `dump`, `build`; ordering rules and the error codes `KERNEL_PIPELINE_00x` | RFC-0004 |
| `com.xihanfun.framework.operation` | `OperationContract`, `OperationSchema`, `OperationHandler<Req, Res>`, `OperationRegistry` with a capacity of 10000, `OperationInvoker` that runs through the full pipeline (XGI: JSON request and response, plus a typed entry point) | RFC-0011 |
| `com.xihanfun.framework.plugin` | The out-of-process plugin runtime: `PluginRuntime.serve(PluginOptions)`, lifecycle hooks `PluginHooks` (configure, start, stop, health), event subscriptions `Subscription` and `EventHandler`, the message catalog handed over in the handshake `PluginCatalog`, host callbacks `Host` (`Host.Invoke` and the batched `Host.Publish`), and `PluginLogger` for JSON-line logs on stderr; the protocol code is in the unexported `com.xihanfun.framework.plugin.v1` | RFC-0017, `plugin/plugin.proto`, `plugin/handshake.md`, `plugin/lifecycle.md`, `plugin/invocation.md` |

Dependency direction between packages: `plugin → operation → pipeline → invocation → primitives`, `plugin → manifest → primitives`. The only external dependency is `jackson-databind`, declared as `requires transitive` in the module descriptor.

The plugin runtime additionally uses grpc-java and protobuf-java. They are optional dependencies of this artifact (`<optional>true</optional>`, `requires static` in the module descriptor), are not passed on to users, and are not referenced by the other packages; applications that write plugins add them themselves, with the same versions as `grpc.version` and `protobuf.version` in this repository's `pom.xml` (the generated code needs a protobuf-java no older than the one that generated it):

```xml
<dependency>
  <groupId>io.grpc</groupId>
  <artifactId>grpc-netty-shaded</artifactId>
  <version>${grpc.version}</version>
</dependency>
<dependency>
  <groupId>io.grpc</groupId>
  <artifactId>grpc-protobuf</artifactId>
  <version>${grpc.version}</version>
</dependency>
<dependency>
  <groupId>io.grpc</groupId>
  <artifactId>grpc-stub</artifactId>
  <version>${grpc.version}</version>
</dependency>
<dependency>
  <groupId>com.google.protobuf</groupId>
  <artifactId>protobuf-java</artifactId>
  <version>${protobuf.version}</version>
</dependency>
```

To use the plugin runtime on the module path, these automatic modules (`io.grpc`, `io.grpc.stub`, `io.grpc.protobuf`, `io.grpc.netty.shaded`, `com.google.protobuf`, `com.google.common`) must be in the module graph: the application `requires` them itself, or uses `--add-modules`.

## Getting Started

Requires JDK 21+. Maven coordinates `com.xihanfun:xihan-framework` (the Maven Central namespace `com.xihanfun` is verified; not yet published):

```xml
<dependency>
  <groupId>com.xihanfun</groupId>
  <artifactId>xihan-framework</artifactId>
  <version>${xihan-framework.version}</version>
</dependency>
```

Using the primitives in a Java application:

```java
record CreateOrder(int quantity) { }
record OrderCreated(String id, int quantity) { }

OperationRegistry registry = new OperationRegistry();
registry.add(OperationContract.of("orders.create").withStability(Stability.EXPERIMENTAL).withExpose(Expose.HTTP),
        CreateOrder.class, OrderCreated.class,
        (context, request) -> request.quantity() > 0
                ? Result.ok(new OrderCreated("o-" + context.correlation().orElse(""), request.quantity()))
                : Result.fail(Error.validation("ORDERS_VALIDATION_001", "orders.quantity.invalid", Map.of("quantity", request.quantity()))));

PipelineBuilder pipeline = new PipelineBuilder()
        .useAt(Middleware.of("Observe", (context, next) -> next.invoke(context)), PipelineStage.OBSERVE, Placement.END, PipelineBuilder.APP_OWNER);
OperationInvoker invoker = new OperationInvoker(registry, pipeline);

Context context = Context.builder().timeout(Duration.ofSeconds(2)).baggage(BaggageKeys.CORRELATION, "c1").build();
OperationResponse response = invoker.invoke(context, OperationRequest.of("orders.create", "{\"quantity\":2}"));
// response.payloadText() == Optional[{"id":"o-c1","quantity":2}]
```

- Recoverable failures return `Result` / `Error` instead of throwing. Error codes follow `<DOMAIN>_<KIND>_<NNN>` with the domain in uppercase, and text uses message keys plus language files (RFC-0010). When there is no resolved text, `Error.message()` resolves it against the process-default catalog of `MessageScope`; if that cannot translate it, it uses the SDK's built-in English templates for kernel messages (`KernelMessages`, identical character for character to `kernel-messages.json`), and finally falls back to a `key (arguments)` description.
- Configuration errors (an invalid manifest, a pipeline cycle, a duplicate operation registration, a full registry) throw `FrameworkException` with an error code; programming errors by the caller, such as malformed arguments, throw `IllegalArgumentException`, and disallowed states throw `IllegalStateException`. Messages are English sentences, with identifiers in single quotes.
- The JSON encoding of `Result<T>`, `Error`, `Maybe<T>` and `TypedId` follows the Result section of RFC-0001: `new ObjectMapper().registerModule(new PrimitivesModule())`. Read text received from the wire with `PrimitivesJson.read(mapper, bytes, type)`, which runs the shared JSON text check first. Lifecycle transition tables, pipeline stage order, error codes, baggage keys and values, the capability requirement grammar, the JSON text check, wire encoding, message templates, kernel errors, manifest reading and writing, payload decoding and pipeline ordering are all verified by `spec/conformance/vectors`, with expected values matching character for character.

### Write a Plugin

A plugin is a child process started by the host: `main` registers operations and subscriptions and hands them to `PluginRuntime.serve`, which reads the environment variables passed down by the host, listens on a local endpoint, writes one handshake line to stdout, and then serves until `Stop` completes, stdin closes or SIGTERM arrives:

```java
public final class GreetingPlugin {
    record Greet(String name) { }
    record Greeting(String text) { }

    public static void main(String[] args) throws Exception {
        OperationRegistry registry = new OperationRegistry();
        registry.add(OperationContract.of("greetings.create").withStability(Stability.EXPERIMENTAL).withExpose(Expose.HTTP),
                Greet.class, Greeting.class,
                (context, request) -> Result.ok(new Greeting("hello, " + request.name())));

        PluginRuntime.serve(PluginOptions.builder()
                .operations(registry)
                .subscribe(Subscription.of("greetings.requested"), (context, envelope, attempt) -> Result.success())
                .catalog(PluginCatalog.load("greetings", locale -> GreetingPlugin.class.getResourceAsStream("Localization/" + locale + ".json")))
                .build());
    }
}
```

The manifest `xihan.manifest.json` lives in the plugin directory. The runtime reads it from the working directory (which is the plugin directory) and hands it to the host unchanged in the handshake, and the host checks that it matches the file in the directory field by field:

```json
{
  "$schema": "https://spec.xihanfun.com/manifest/v1.json",
  "id": "xihan.samples.greeting",
  "version": "0.1.0",
  "primitives": "1",
  "stability": "experimental",
  "kind": "plugin",
  "isolation": "out-of-process",
  "contributes": { "operations": [ "greetings.create" ], "health": [ "greeting" ] },
  "permissions": [ "capability:kernel.pipeline" ],
  "activation": [ "onStartup" ],
  "entry": "greeting"
}
```

- `kind` is `plugin` and `isolation` is `out-of-process`; do not write `contributes.pipeline` (only Wasm plugins can contribute middleware); `primitives` equals the primitives major version this SDK supports, `1`; the registered operations are unique and all appear in `contributes.operations`, and no (topic, type) pair is subscribed twice. Otherwise the runtime refuses to start (`handshake.md` §1): it does not listen, writes no handshake line, logs one `error` on stderr, and `serve` throws a `FrameworkException` with the error code (such as `PLUGINS_VALIDATION_001` or `PLUGINS_VALIDATION_004`).
- The health items reported by the hook must appear in `contributes.health`; others are dropped, with one `warning` per name. To call back the host, declare `capability:kernel.pipeline` (`Host.Invoke`) or `capability:messaging.queue` (`Host.Publish`) in `permissions` and have the host grant it in `Configure`: the runtime checks both locally before it sends a callback, and when either is missing the callback fails with `PLUGINS_DENIED_002` + `plugins.callback.denied` without a request.
- `entry` is the executable relative to the plugin directory (on Windows, the host appends `.exe` when there is no extension). The `entry` of a Java plugin points to a launcher script: an executable sh script with a shebang on Unix, and a `.cmd` on Windows. The host passes on only the environment variables listed in `handshake.md` §1, and `JAVA_HOME` is not one of them, so the script writes the absolute path of `java` and the full class path, for example `exec /opt/java/bin/java -cp '/opt/greeting/lib/*' GreetingPlugin "$@"`.
- Call back the host with `Host.of(context)` in a handler: `invoke(context, "orders.create", payload)` invokes an operation through the host's full pipeline, and `publish(context, envelopes)` publishes in a batch, with one result per item.

Verify it with the black-box runner of the spec repository (requires Go; see `spec/conformance/README.md` for the options):

```bash
cd spec/conformance
go run ./cmd/xihan-conformance plugin --dir <plugin directory> --sample 'greetings.create={"name":"hi"}'
```

The complete example is in `examples/echo`: four operations (echo, relay through a host callback, a deliberate crash that is excluded from verification, and listing the received events), one event subscription, one health item and the configuration section `XiHan:Echo`. The test `EchoConformanceTest` puts it in a temporary directory, generates the launcher script for the current platform, and runs every case of the black-box runner from the submodule.

## Behavior Shared with the Host

Behavior unified by the spec's ADR-0233, ADR-0235, ADR-0236 and ADR-0237, the same in every language SDK and in .NET:

- **JSON text**: the wire encoding of Result and Error, operation payloads and manifests all go through the same check first (`JsonText.check`, vector `json-text.json`): syntax follows RFC 8259 (no comments, trailing commas, `NaN`, leading zeros, plus signs or multiple root values; empty text and whitespace-only text are invalid too), the text is UTF-8, and a leading BOM is a syntax error; nesting is at most 64 levels; strings and member names must be valid Unicode (rejecting invalid UTF-8, overlong encodings, surrogates encoded as UTF-8, raw control characters, invalid escapes and lone surrogate escapes); and no level may contain a duplicate member (compared after unescaping). Syntax errors take precedence and report only `$` as the location; otherwise the path of the first duplicate is reported. Jackson skips a BOM, guesses UTF-16 from the bytes and lets lone surrogates through, so this pass does not go through Jackson.
- **Wire encoding**: a successful result with no value (`Result<Unit>`) is written only as `{"ok":true}`; the no-value case of `Result<Maybe<T>>` is `"value":null`. The `message` of an `Error` is required and non-empty; a missing `messageKey`, `details` or `inner` means there is none, and writing them as `null` is invalid; unknown members are ignored. Duplicate members are invalid at any level, including inside `value`, `details` and `inner` (the previous version did not check inside `value`); the decoder checks duplicates, the 64-level limit and lone surrogates itself, regardless of the `ObjectMapper` configuration. Numbers follow the value model: integer literals within the 64-bit range round-trip unchanged (9007199254740993 does not become 9007199254740992), and everything else is a double-precision float; floats with integral values in details are written as `2.0`, `-0.0`, `1.0E17`, and non-finite values as the strings `"NaN"`, `"Infinity"`, `"-Infinity"` (previously, non-finite values were not allowed in details).
- **Templates**: message keys are at most 128 characters long. Format specifiers are recognized only if they match `^[DdFfNnXx][0-9]{0,2}$`: `D` and `X` apply only to integers, `X` only to non-negative integers, and `F` and `N` to integers and floats; specifiers that do not apply or are not recognized (`E2`, `G`, `0.00`, `yyyy`, `D100`, ones containing spaces) are all written as unformatted (the previous version allowed precision up to 99). `F` and `N` expand to the exact decimal and round exact halves to even (0.125 with `F2` gives `0.12`, 2.675 with `F2` gives `2.67`), write all integer digits, and keep the minus sign when a negative number rounds to zero. Arrays and objects are written as compact JSON, with object members ordered by the UTF-16 code units of their names, and containers nested deeper than 64 levels written as `null` (the previous version used Java's `toString`). Floats with 1e-4 ≤ |x| < 1e17 are written without an exponent; outside that range they are written as `1E+17`, `9.9E-05`, `5E-324`, and negative zero as `-0`. `Describe` orders its arguments by the ordinal order of their names.
- **Locales**: `MessageTemplate.format(template, arguments, locale)` / `tryFormat(…, locale)` / `text(value, locale)` and `MessageCatalog.resolve(key, locale, arguments)` take the decimal separator and the group separator from the locale: de-DE, es-ES and pt-BR use `,` and `.`, fr-FR uses `,` and U+202F, ru-RU uses `,` and U+00A0, and every other locale, or no locale, uses `.` and `,`; locale names are case-insensitive. The decimal separator applies to unformatted floats (including the mantissa of an exponent form; 1.5e20 in de-DE is written `1,5E+20`) and to `F` and `N`; the group separator applies only to `N`. Unformatted integers are not grouped, and `D`, `X` and numbers inside arrays and objects do not vary by locale. `Error.message()` takes its symbols from the process-default locale of `MessageScope`, including when it falls back to the built-in en-US templates.
- **Kernel errors**: error codes, message keys and arguments follow `kernel-messages.json`, and the built-in English templates are identical to it character for character, including the 9 keys for manifest reading, so the `message` of a manifest read failure is the same English sentence as in .NET; `kernel.operation.type_mismatch` carries only `id` (the previous version carried the Java type names `expected` / `actual`). Duplicate registration and a full registry at configuration time still throw `FrameworkException`, and `toError()` yields the error with its key and arguments.
- **Built-in steps of the invoker**: they sit in the same positions as the built-in middleware of .NET, all placed at `Beginning` of their stage under the owner `xihan.kernel.core` (`OperationInvoker.KERNEL_OWNER`), and ordered among other middleware at the same position by the ordinal order of the owner, then by registration order within the same owner (built-in steps are registered after the user's middleware). The Observe stage translates exceptions (`KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`; the error of a `FrameworkException` goes into `inner`, exceptions caused by cancellation are attributed by token, and `java.lang.Error` is not translated), and catches only exceptions from what is ordered after it: exceptions thrown by middleware in the Ingress stage, and by middleware at `Beginning` of the Observe stage whose owner is ordered before it (such as `app`), are passed to the caller unchanged. The Resilience stage checks the deadline: if it has already passed on entry, the result is `KERNEL_TIMEOUT_001` + `kernel.invocation.deadline_before_start` (the previous version checked before the first middleware; withdrawn); when the downstream writes a cancellation as its result (`KERNEL_CANCELLED_001`) after the deadline token has fired, the result becomes `KERNEL_TIMEOUT_001` + `kernel.invocation.deadline_exceeded`, even when the caller cancelled too (RFC-0003 rule 1; the previous version returned the cancellation as it was), and a thrown cancellation is attributed by the same rule in the Observe stage. The Validate stage decodes the payload of a raw invocation, and typed invocations skip it. Before entering the pipeline, only an unregistered operation (`KERNEL_NOTFOUND_001`) and a type mismatch in a typed invocation (`KERNEL_VALIDATION_002`) are checked, in that order. The invoker copies the user's `PipelineBuilder` (`copy()`) before adding the built-in steps, leaving it unchanged.
- **Response encoding**: the XGI entry point encodes the response into a payload only after the pipeline has finished, so middleware sees the result before encoding; `Operations.findResponse(context)` gives the response object from a successful handle stage (the previous version's `findResponsePayload` gave the payload; withdrawn). When the response cannot be written (a float member of a typed response is NaN or infinite, or a value is not supported by serialization), the invocation ends with `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`, with the error of a `FrameworkException` in `inner` if one is on the exception chain; nothing is thrown to the caller, and there is no payload (the previous version used the English message of `Error.literal`). NaN is not written as a string: encoding turns off Jackson's `WRITE_NAN_AS_STRINGS`, and the written text goes through the shared JSON text check again. The typed entry point does not encode.
- **Cancellation only through tokens**: the invoker and the built-in steps do not interrupt threads or cancel futures; they only fire the context's token. If a handler still returns a result after the token has fired, the invocation ends with that result. A handler that needs to finish early checks `context.cancellation()`, `onCancelled` or `awaitCancellation` itself.
- **Payload decoding**: the shared check runs first (syntax errors report `$`, duplicate members report the path of the first duplicate, ahead of any type problem); an empty payload is equivalent to `{}`, and whitespace only is a syntax error (the previous version treated it as `{}`). The payload is then checked against the request type in text order (`RequestShape`, independent of Jackson's read order): member names are case-sensitive, unknown members are ignored, numbers are not read from strings, integers do not accept `1.0` or `1e2`, a value outside the type's range is a mismatch, floats accept integer literals, 1e400 overflows to infinity and 1e-400 becomes 0; a missing required member is reported at the end of its enclosing object, with that object's path. Payload text is compared as JSON values; whitespace, escapes and the spelling of numbers are not part of the contract. Members of arbitrary JSON type (`JsonNode`, `Object`) keep the value as read: integers beyond double precision stay exact, `2.0` and `2`, `-0.0` and `0` stay distinct, and numbers a double cannot represent, such as `1e400` and `1e-400`, keep the exact decimal of the original text; written back, they are equal as JSON values and do not turn into `null`, infinity or 0. `reason` carries only the path: `$` when the payload is `null`, is not an object, or fails at the root; `$['name']` when the member name contains `.`, a space, `'`, `/`, `"`, `[`, `]`, `(`, `)`, `\`, tab, line feed, carriage return, form feed, backspace, U+0085, U+2028 or U+2029; and `$.name` otherwise.
- **Manifest reading**: in the order JSON text → literal `null` → item-by-item schema check → cross-field constraints, each step reports only the first problem, and every error code is `KERNEL_CAPABILITY_006` (the previous version used `PRIMITIVES_VALIDATION_001` with an English message): `kernel.manifest.invalid_json` (`reason` is `$` or the path of the first duplicate), `kernel.manifest.empty` (the root is `null`; no arguments), `kernel.manifest.invalid` (`reason` is the path of the first problem: members are checked in text order, each in turn for being outside the schema → `null` → type → value, and after an object is done, missing members are checked in the order of `required`); cross-field constraints are checked in the order `primitives.manifest.isolation_required` → `isolation_not_allowed` → `duplicate_provides` → `duplicate_requires` → `duplicate_bindings`, with `id` as the only argument. `ManifestJson.read(byte[])` does not skip a BOM; `readFile` reads UTF-8 and skips a leading UTF-8 BOM, and a missing file is `kernel.manifest.file_missing` (argument `path`; previously it threw `IOException`). Interface versions have no leading zeros and do not exceed 2147483647, and only requirement versions may carry a single `^`; middleware names are non-empty, `contributes.health` is checked against `^[a-z][a-z0-9.-]*$`, and duplicates in `contributes.permissions` report the second occurrence; an `activation` written as an empty array is invalid. Middleware contributed by non-Wasm plugins is left for the host to reject at discovery, and reading and building manifests no longer check it (consistent with .NET). Cross-field constraints in `Manifest.Builder.build()` carry the same message keys and `id`, with the error code `PRIMITIVES_VALIDATION_001`.
- **Manifest writing**: the layout of `ManifestJson.write` is fixed character for character by the Writing section of RFC-0002: two-space indentation, LF, no trailing newline, `": "`; `$schema` is always written as `https://spec.xihanfun.com/manifest/v1.json`, lists are always written (an empty list as `[]`), an omitted `role` is written as `provider` and an omitted `activation` as `["onStartup"]`, requirements always write `optional`, bindings always write `required`, middleware always writes `before` / `after`, and `contributes` is always written; strings escape only `"`, `\`, control characters and lone surrogates (`<`, `&`, U+2028 and non-ASCII are written as is). The previous version omitted default values and escaped `<>&`. `Manifest` compares by effective values (ignoring `$schema`; unwritten roles, activation events, contribution points and the `required` of bindings take their defaults), and a written manifest, read back, equals the original.
- **Grammar**: every regular expression in the spec is a whole-string match, with no exception for a trailing newline (`xihan.tenant\n` and a `traceparent` with a newline do not pass); Java always uses `Matcher.matches()`. Versions in capability requirements do not accept leading zeros, `+`, whitespace or values above 2147483647.
- **Baggage values**: values of registered keys must be non-empty, at most 256 UTF-16 code units long, and free of U+0000–U+001F and U+007F–U+009F. For external input, `Context.builder().baggage(…)` drops members that do not conform and keeps an existing value of the same name; for in-process derivation, `withBaggage` throws `IllegalArgumentException` when a registered key is given a non-conforming value (the previous version removed the key). `xihan.idempotency-key` is exempt in both cases.
- **Tracing**: `traceparent` is accepted only if it matches `^00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}$` and its IDs are not all zeros; an invalid one is treated as absent. Only the sampled bit is taken, and only `00` / `01` is written (the previous version kept the whole flags byte and had `traceFlags()`; withdrawn); without an upstream, `01` is written.
- **Pipeline**: duplicate registration, unknown stages, and constraint subjects that are unregistered or ambiguous by name are reported at registration; constraint targets that are unregistered or ambiguous, cross-stage constraints and cycles are reported at ordering time (`describe` / `dump` / `build`). Like .NET, ordering processes one stage at a time: within a stage, it resolves the constraints of each subject in baseline order (before first, then after, each in declaration order) and sorts only after resolving them all, so when several errors exist at once, the same one is reported. Name-based constraints use the same matching as .NET: an instance registered by name matches only its instance name, and a registration without a name matches the middleware name (in the previous version, the middleware name could also match an instance registered by name). Error messages are the original .NET English text, with an instance registered by name written as `TypeName[name]`; for a cycle, all middleware still blocked is listed in baseline order, for example `Middleware ordering constraints in stage 'validate' form a cycle: 'Guard[a]', 'Guard[b]'.`.
- **Plugin start and handshake** (RFC-0017, `plugin/handshake.md`): the manifest and the declarations are checked before listening, and the runtime refuses to start when they do not match. The address in the handshake line contains no whitespace, where whitespace is the set listed by the spec (the same as `\s` in .NET regular expressions, including U+0085, U+00A0, U+2007, U+202F and U+3000 but not U+001C–U+001F or U+200B, unlike `Character.isWhitespace`); `tcp` is always written as `127.0.0.1:<port>`. The code that parses handshake lines and endpoints follows the same grammar: the address is one or more characters other than whitespace (non-ASCII letters and `;` may appear), and `tcp` accepts only the dotted decimal of `127.0.0.0/8` with four parts and no leading zeros, or `[::1]`, with a port of 1–65535 without sign or leading zeros (vector `handshake-lines.json`). Every RPC from the host first checks the metadata `xihan-plugin-session` in constant time: there must be exactly one value, and no value, a mismatch, or two or more values (even when one is right) are rejected with `Unauthenticated` and nothing runs; the token comes before everything else, including the order check and reading the first frame of a stream. The handshake selects the highest version shared with the host's list (vector `protocol-versions.json`) and refuses with `FailedPrecondition`, leaving the state unchanged, when there is none; `primitives` is the manifest's value, `manifest` is the text of the manifest file without a leading UTF-8 BOM, only unary operations are declared, subscriptions are written in declaration order with `mode` always `competing` or `broadcast`, and `catalogs` holds only the author's catalogs: the SDK runtime's catalog is not sent in the handshake.
- **Plugin call order and lifecycle** (`lifecycle.md` §7): `Handshake` is accepted only in `Declared`, `Configure` only in `Resolved` and `Start` only in `Configured`, once each; `Stop` is not accepted in `Declared`, `Draining` or `Stopped` or while another stop is in progress; any combination not in the order table is refused with `FailedPrecondition`, does nothing and leaves the state unchanged. An empty configuration section is `{}`; one that is not a JSON object (after the shared JSON reading check) does not reach the configure hook and moves the plugin to `Failed` with `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` (`phase` `configure`, `reason` `the configuration is not a JSON object`). After the start hook succeeds the plugin is `Started`, asks the health hook once and enters `Ready`, `Degraded` or `Failed` by the result (`Ready` when there is no health hook or it reports another state, `Degraded` when it throws), and only then answers `Start`. Only `Ready` and `Degraded` serve; calls and deliveries in any other state fail with `PLUGINS_UNAVAILABLE_001` + `plugins.process.unavailable` (`state` is the state name). `Health` may be called in any state: before `Start` it reports the local state (`Declared`, `Resolved` or `Configured`) with no health items and without calling the hook; in `Ready` and `Degraded` every call asks the health hook, the `Ready`, `Degraded` and `Failed` it reports change the state by the legal transitions (`Failed` never comes back), other states change nothing, and when the hook throws this result is `Degraded` with no health items and the error `plugins.process.failed` (`phase` `health`), and the state moves to `Degraded` as if the hook had reported it, later results deciding the state as usual; `Draining`, `Stopped` and `Failed` no longer call the hook. `WatchHealth` pushes the current state first, then every change of state, health items or error, asks the hook every 10 seconds while serving, pushes once on entering `Draining`, and ends the stream after answering `Stop` (the previous version polled every second and ended the stream on `Draining`).
- **Plugin stop and shutdown** (`lifecycle.md` §7.5–§7.7): when the start hook has never succeeded, `Stop` does not call the stop hook, answers `ok` and exits with code 0; `Started`, `Ready` and `Degraded` enter `Draining` (a plugin whose health hook reported `Failed` does not move), reject new calls, wait for in-flight calls up to the grace period (`grace_seconds` 0 means 5 seconds), then signal their cancellation without waiting further, call the stop hook (with the `reason` as it came), answer, enter `Stopped` and exit. The stop hook is called at most once per process; a failure it returns or throws goes into `StopResponse.status` and the process exits as usual (the previous version called the stop hook once `Configure` had run). Reading stdin to its end (or a read error) and SIGTERM are both requests to wind down: a serving plugin enters `Draining` (other states do not move), signals the cancellation of every in-flight call at once and waits for them, and a plugin whose start hook succeeded calls the stop hook once if it has not been called (`reason` `shutdown`); at most 3 seconds after the request, the process ends with exit code 0 whether or not this has finished, and a `Stop` in progress is bound by the same 3 seconds. When a lifecycle or health hook throws, `reason` is the simple type name of the exception (such as `IllegalStateException`; an anonymous class gives its binary name without the package, such as `EchoPlugin$1`) without the exception text, which goes only to stderr.
- **Plugin calls and deliveries** (`invocation.md` §1–§4): `Invoke` checks, in order, the token, that the operation is declared in the handshake (otherwise `Unimplemented`) and that the plugin serves (otherwise `PLUGINS_UNAVAILABLE_001`), then restores the context and runs through the invoker and the full pipeline, with an empty payload meaning `{}` (the previous version reported unavailability first). `InvokeStream` reads the first frame: a stream that ends before its first frame, or whose first frame is not `start`, ends with `InvalidArgument`, and a first frame `start` always ends with `Unimplemented`, whether the operation is declared and whether the plugin is ready; this SDK has no public API for streaming operations. The context: `trace_parent` follows the RFC-0003 grammar, and an invalid one means no parent span; `trace_state` does not enter the context; only registered baggage keys are kept; `deadline` is read by the strict grammar (vector `deadlines.json`; `Instant` has nanosecond precision, so nine fraction digits are not truncated), an unreadable one counts as none, and the effective deadline is the earlier of it and the gRPC deadline; gRPC cancellation cancels the context. `HandleEvent` checks, in order, the token, that there is an `envelope` and `mode` is empty, `competing` or `broadcast` (otherwise `InvalidArgument`), the subscriptions by (topic, mode, type) (none gives `KERNEL_NOTFOUND_001` + `plugins.event.unsubscribed` with `id`, `topic`, `type` and `mode`, an empty mode written as `competing`) and that the plugin serves, then hands the message to every matching subscription in declaration order, the first failure ending the delivery as its result (the previous version handed it only to the first); a handler that throws gives `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`.
- **Plugin errors, message keys and logs** (`invocation.md` §3, §8): an `Error` with a message key is written with `text` empty, for the host to translate into the caller's language through its catalogs, and only free-text errors write `text` (the previous version rendered them in `XIHAN_PLUGIN_LOCALE`); `details` is written by the value model and is empty when there are none; `inner` is written too. Reading an error written by the host: a `code` that does not match the error code grammar replaces the whole error with `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` (`phase` always `invoke`, for the results of `Host.Publish` too; `reason` `invalid error code '<code>'`; the original `inner` is dropped); a `message_key` that matches the grammar is used as a key and `text` is not taken, and otherwise the error is free text (from `text`, or `code` when `text` is empty); `details` that is empty, only whitespace, the empty object `{}`, fails the shared JSON reading check, is not an object, or has a number at any level that overflows a double counts as no details (an underflow reads as 0, an integer beyond 64 bits as a double), and `inner` follows the same rules (the previous version replaced the whole error with `plugins.process.failed`); `ok` false without an error, or a missing `status`, is `plugins.process.failed` (`phase` the operation ID or `publish`, `reason` `the host reported a failure without an error`). Vector `error-reading.json`. The runtime's seven message keys, their arguments (which are the members of `details`) and error codes follow `plugin-messages.json`, and `PluginMessages` carries the same 10-locale catalog as the reference implementation for local rendering. Each stderr line is one JSON object (`level`, `message` and scope properties), and the root logger of `java.util.logging` is rewritten to such lines as well.
- **Callbacks** (`invocation.md` §5, `handshake.md` §4): at start the runtime parses `XIHAN_PLUGIN_HOST_ADDRESS`: one or more `<network> <address>` separated by `;`, the whole value invalid when any entry is (vector `host-addresses.json`); it takes the first endpoint in the host's order of preference that this SDK can dial (loopback TCP, plus Unix domain sockets on Linux with epoll; grpc-java cannot dial named pipes) and keeps it. The host always puts a loopback TCP endpoint last, so the .NET host on Windows (a named pipe plus loopback TCP) can be called back too. When the variable is missing or invalid or no entry can be dialed, the plugin serves as usual, logs one `warning` on stderr at start, and every callback fails with `PLUGINS_UNAVAILABLE_001` + `plugins.host.unavailable` (`reason` `no supported callback endpoint`) without a request (the previous version refused to start on an invalid variable). Before sending, the runtime checks locally in the host's order: the required permission (`capability:kernel.pipeline` for `Host.Invoke`, `capability:messaging.queue` for `Host.Publish`) is both in the manifest's `permissions` and among the permissions granted in `Configure`, otherwise `PLUGINS_DENIED_002` + `plugins.callback.denied`; the callback context's `xihan.tenant` is the tenant of a call or delivery being handled at the moment, otherwise `PLUGINS_DENIED_002` + `plugins.callback.tenant_denied`; last, no request is sent either when the callback context's deadline has passed or it has been cancelled, with the result of the matching row of the table (`KERNEL_TIMEOUT_001` for a passed deadline, `KERNEL_CANCELLED_001` for a cancellation); for `Host.Publish` these are all results for the whole batch. The order is endpoint, permission, tenant, then deadline and cancellation. The `xihantenant` of an envelope is not checked locally and is left to the host item by item (the previous version checked it locally). The callback metadata comes from the context of the call: the traceparent of the current span, `deadline` in UTC with seven fraction digits and `+00:00`, the registered baggage and an empty `trace_state`; the gRPC deadline equals `deadline` and the session token is attached; a caller cancelling the context cancels the callback, while a deadline is not cancelled locally: grpc-java ends the call with `DeadlineExceeded` at the same deadline, and the result follows the table only, never rewritten by the clock or the tokens. gRPC statuses are mapped by the table in §5 (vector `callback-status.json`): `Unauthenticated` is `plugins.callback.session_invalid`, `PermissionDenied` is `plugins.callback.denied`, `DeadlineExceeded` is `KERNEL_TIMEOUT_001`, `Cancelled` with the context's cancellation signal fired is `KERNEL_CANCELLED_001`, any other `Cancelled`, `Unavailable` and connection failures are `plugins.host.unavailable` (`reason` `<status name>: <description>`, the status name in PascalCase), `Unimplemented` and `InvalidArgument` of `Host.Invoke` are `kernel.operation.unknown` and `kernel.operation.invalid_payload` (`reason` the status description), and everything else, including those two for `Host.Publish`, is `plugins.process.failed` (`phase` the operation ID or `publish`). When the `Host.Publish` RPC fails, every item gets the same error, and when the number of results differs from the number of envelopes, every item is `plugins.process.failed` (`reason` `the host returned <n> results for <m> envelopes`).

## Language Mapping

How Java constructs map to the spec:

- **Value model of template arguments** (RFC-0010, Templates): `null` is the null value; `Boolean` is a boolean; `String`, other `CharSequence` types and `Character` are strings; `Byte`, `Short`, `Integer`, `Long`, `AtomicInteger` and `AtomicLong` are 64-bit integers, and `BigInteger` is an integer within the 64-bit range and a double-precision float beyond it; `Double` is a float, while `Float` and `BigDecimal` are first converted to the nearest `double` (`0.1f` is written `0.10000000149011612`, `new BigDecimal("2.50")` is written `2.5`); a `Map` whose keys are all `String` is an object, and `Collection` and Java arrays (including primitive arrays) are arrays. Values outside the model (enums, `UUID`, `java.time` types, a `Map` whose keys are not all strings, and so on) are written as the text of `toString()`, and as a JSON string of that text when nested in an array or object; they do not cross languages, so a plugin that needs cross-language formatting converts them to strings first.
- **Numbers in the wire encoding**: `Error.details()` may hold `Integer` / `Long` / `BigInteger` / `Float` / `Double` / `BigDecimal`, all written according to the value model above; read back, integers within the 64-bit range are `Integer` or `Long`, everything else is `Double`, and non-finite values come back as strings. The content of `Result.value` is written by the value type's own Jackson configuration; when reading, integers beyond 64 bits first become floats according to the value model, and are then handed to the value type.
- **Payload request types**: declare them as records or as classes with Jackson annotations. Mark required members with `@JsonProperty(required = true)` and leave optional members unannotated (when missing, they take Java's default: 0 / `false` for primitive types, `null` for reference types). `String`, `List` / arrays / other collections, `Map`, nested records and `JsonNode` / `Object` accept `null` (meaning no value); integers, floats and booleans, whether primitive or boxed (`Long`, `Double`, `Boolean`), do not accept `null`, and neither do their list items and map values. Types that are not recognized (enums, `java.time`, `Optional`, the primitives' `Maybe` / `TypedId` and other types with custom decoders, polymorphic types) are handed to Jackson individually at the position where they are read, and a failure reports the path given by Jackson; `byte[]` reads a Base64 string as Jackson does.
- **Text and bytes**: `JsonText.check(String)`, `ManifestJson.read(String)` and `PrimitivesJson.read(mapper, String, …)` first encode the string as UTF-8; a lone surrogate in the string (which cannot be encoded as UTF-8) is treated as a syntax error, rather than replaced with `?` as `String.getBytes` does.
- **The `Error` name**: `com.xihanfun.framework.primitives.Error` has the same name as `java.lang.Error`, so import it explicitly in files that use it; it is not a `Throwable`, so misuse is reported at compile time.
- **Plugin hooks and callbacks**: the methods of `PluginHooks` all have default implementations and return `Result<Unit>`, and a failure is handed to the host as it is; one that throws (or returns `null`) gives `PLUGINS_UNEXPECTED_001` + `plugins.process.failed` with the simple type name of the exception as `reason`, a `FrameworkException` included, whose error does not go into `inner` (the previous version used the qualified class name or the exception message). An empty result from `health()` means there is no health hook. `PluginConfiguration.decode(type)` runs the shared JSON text check first and then reads with Jackson: member names match by ASCII case only: before Jackson reads the section, member names are rewritten to the property names of the target type level by level (records and ordinary classes, lists, arrays and map values), an exact match first, with only `A`–`Z` equal to their lowercase, so U+212A (the Kelvin sign) is not `k` and the case of non-ASCII letters does not fold (the previous version used Jackson's `ACCEPT_CASE_INSENSITIVE_PROPERTIES`, which lowercases by Unicode); the rewrite changes only names and keeps the text of numbers; a string leaf read as a number must follow the JSON number grammar (`" 7"`, `+7`, `07` and `NaN` do not, and an accepted text is read as the same JSON number), and a string leaf read as a boolean must be `true` or `false` (ASCII case-insensitive; characters such as `ſ` whose case mapping lands on ASCII do not count); unknown members are ignored. An exception thrown by an event handler is translated into `KERNEL_UNEXPECTED_001`. The contexts the runtime hands to handlers and hooks always carry a `Host` (without a usable callback endpoint the callbacks fail instead of `Host.of` being empty); `Host.invoke` returns an `OperationResponse`, and `Host.publish` returns a `List<Result<Unit>>` with one result per envelope. The spec fixes the shutdown limit at 3 seconds, so `PluginOptions.Builder.shutdownGrace` is removed. On SIGTERM the shutdown hook winds down and ends the process with `Runtime.halt(0)` (otherwise the JVM exits with 143); an author's own `System.exit` while serving goes through the same hook and also ends with exit code 0.

## Design

**Concurrency: synchronous signatures on virtual threads, not `CompletableFuture`.** Middleware, handlers and the invoker are all synchronous methods (`Result<Unit> invoke(Context, Step)`, `Result<Res> handle(Context, Req)`), designed for Java 21 virtual threads (JEP 444): a virtual thread blocked waiting on I/O yields its carrier thread instead of occupying a platform thread, so call stacks and exception stack traces stay readable and no layer has to be rewritten as a callback chain. To that end, the built `Step`, `OperationInvoker` and `OperationRegistry` are immutable or thread-safe and can be used by any number of threads at once; `Context` is immutable and passed by derivation, and the state of each operation invocation travels with the derived context (`Context.withValue`), so nested and concurrent invocations do not interfere with each other; locks are always `ReentrantLock`, and nothing blocks inside `synchronized` (on Java 21, `synchronized` pins virtual threads).

**Cancellation and deadlines are modeled by the SDK itself.** `Context` has two tokens: the deadline token is fired by a timer at the deadline, and the external token by `CancellableContext.cancel()`; cancelling a parent cancels its children, and cancelling a child does not affect the parent. Attribution looks only at the tokens (RFC-0003 rule 1, RFC-0004, ADR-0095): if the deadline token has fired, the result is `KERNEL_TIMEOUT_001`, whether or not the caller has also cancelled; only when just the external token has fired is it `KERNEL_CANCELLED_001`. `onCancelled` registers a callback (run immediately if already cancelled), and `awaitCancellation` waits on a virtual thread; the `CancellableContext` returned by `withCancellation` / `withDeadline` / `withTimeout` must be closed after use (try-with-resources), so that long-lived parents do not accumulate finished children.

**JSON: Jackson.** The Java standard library has no JSON, and XGI payloads, manifest reading and the wire encoding all need it. `jackson-databind` was chosen because it is the de facto standard on the JVM, is itself a JPMS module and supports records, and users of common libraries such as grpc-java usually already have it. The core primitive types do not depend on Jackson (RFC-0001: the primitives layer contains no serialization code): the shared JSON text check `JsonText` is a hand-written byte-by-byte checker, and the encoding lives in the `primitives.json` package; manifest uses only the tree model to check item by item against the schema (`ManifestShape`), with no reflective binding, and writing uses a hand-written layout; operation uses `OperationJson.newMapper()` (which registers the primitives encoding, ignores unknown fields and fails on any type mismatch), and before deserializing checks the payload against the request type in text order (`RequestShape`), so the order in which errors are reported does not depend on Jackson's internal paths. Applications on the module path must `opens` the packages containing their request and response types to `com.fasterxml.jackson.databind`.

**Nullability.** Public members neither accept nor return `null`: values that may be absent are returned as `Optional` (`findBaggage`, `find`, `tenant()`), data fields that need wire encoding use `Maybe` (encoded as the value or `null`, and an object missing the field also decodes to no value), and absent collections are empty collections; passing `null` as an argument throws `NullPointerException`.

**Bounded.** The item bag holds at most 1024 entries, baggage at most 180, values passed by derivation at most 256 keys, and the operation registry 10000 operations; exceeding these is a programming or configuration error. Pipeline middleware and ordering constraints have no limit, consistent with the .NET `PipelineBuilder`: they are registered by code at startup and do not come from external input (the previous version limited them to 1024 middleware and 4096 constraints; withdrawn).

**Plugin runtime: grpc-java, with the generated code committed.** The transport is grpc-java's Netty transport (`grpc-netty-shaded`, which bundles a relocated Netty that does not clash with the application's own Netty) plus `protobuf-java`, and the server runs every call on `Executors.newVirtualThreadPerTaskExecutor()`, so handlers, hooks and callbacks may block. The protocol code is generated from `spec/plugin/plugin.proto` and committed to `src/main/java/com/xihanfun/framework/plugin/v1` instead of being generated on every build: the build does not need to download native protoc binaries, it is the same on every platform, and the generated code can be reviewed; `plugin.proto` has no Java options, so the `protocol` profile copies it and appends `java_package` and `java_outer_classname` at the end, and CI regenerates it and checks that nothing differs. The generated code does not relax the gates and passes `-Xlint:all -Werror` and doclint as well. Endpoints: on Linux, when the epoll native library bundled with grpc-netty-shaded is available (x86_64, aarch_64), the runtime listens on a Unix domain socket placed in a private directory newly created by the process (random name, `0700`, socket `0600`); on Windows, macOS and in other cases, it listens on a random port of the loopback TCP address `127.0.0.1` (allowed by the spec; other users on the same machine can connect, so isolation relies only on the session token). This SDK does not listen on named pipes, so the access control of named pipes does not apply. Callbacks likewise can dial only loopback TCP and Unix domain sockets on Linux (grpc-java does not support named pipes); by the spec the host always puts a loopback TCP endpoint last in the callback list, so the .NET host on Windows can be called back as well. Since JDK 23, the `sun.misc.Unsafe` memory access used by Netty prints warnings on stderr; add `--sun-misc-unsafe-memory-access=allow` to the launcher script (JDK 21 does not have this option). The runtime's own message keys (`plugins.*`) are keys fixed by the spec and shared with the host (`invocation.md` §8); the host has catalogs for them, so errors with these keys leave `text` empty and the catalog is not sent in the handshake, while the language files of `PluginMessages` for 10 locales (the same texts as the reference implementation) serve local rendering in the plugin.

## Development

Without Maven installed locally, build and test with the official Docker image, caching dependencies in a named volume:

```bash
git submodule update --init          # spec/
```

PowerShell:

```powershell
docker run --rm -v "${PWD}:/src" -v xihan-sdk-java-m2:/root/.m2 -w /src maven:3-eclipse-temurin-21 mvn -B verify
```

Git Bash (with path conversion turned off):

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "$(pwd -W):/src" -v xihan-sdk-java-m2:/root/.m2 -w /src maven:3-eclipse-temurin-21 mvn -B verify
```

With Maven 3.9+ and JDK 21+, run `mvn -B verify` directly. Gates: `maven.compiler.release` 21, compilation with `-Xlint:all -Werror` and `-Xdoclint:all,-missing`; tests use JUnit 6 (JUnit Platform) and run on the class path, and conformance vectors are read by relative path from the repository root (vector files are not copied). `VectorCoverageTest` checks the vectors of the claimed conformance profiles against `spec/conformance/profiles.json`: when the spec adds a vector to a claimed profile, it fails until a test replays the file or the file is listed as a gap with a reason. Do not commit the `target/` that the container writes as root.

The example plugin `examples/echo` is compiled with the tests and passes the same gates. The conformance test `EchoConformanceTest` needs Go on PATH (see `spec/conformance/go.mod` for the version): it runs `go run ./cmd/xihan-conformance` in `spec/conformance`, so the runner comes from the same commit as the locked spec; without Go, the test fails, and it is skipped (printing the reason) only when `XIHAN_CONFORMANCE_REQUIRED=0` is set. The `maven` image above has no Go; to run it in a container, use an image with Go installed as well, or install JDK 21+ and Go locally and run `mvn -B verify` directly; to skip it in that image, add `-e XIHAN_CONFORMANCE_REQUIRED=0` to `docker run`.

After `spec/plugin/plugin.proto` changes (a submodule upgrade), regenerate the protocol code with `mvn -B -Pprotocol process-sources`; in Docker, replace the `verify` at the end of the commands above with `-Pprotocol process-sources`. protoc and protoc-gen-grpc-java are taken from Maven Central, with the versions `protobuf.version` and `grpc.version` in `pom.xml`; the generated code replaces `src/main/java/com/xihanfun/framework/plugin/v1` as a whole and is committed together with the sources.

## Status

`0.1.0-SNAPSHOT`: primitives, manifests, the invocation context, the pipeline, operations and the out-of-process plugin runtime (`plugin`, `xihan.plugin.v1`, grpc-java) are usable, and the example plugin `examples/echo` passes all 14 cases of the spec repository's black-box runner (over a Unix domain socket on Linux, and over loopback TCP with a `.cmd` launcher on Windows); the operation sets for remote providers (such as `caching.distributed@1`) are not provided yet. For the official release, `-SNAPSHOT` will be dropped and the SDK published to Maven Central under the `v0.1.0` tag.

Per RFC-0024:

- Spec version: pinned to framework-spec commit `386501f`; the spec has no tag yet, and its first tag is planned as `v1.0.0-rc.1`.
- Claimed profiles: `core` and `plugin` (`spec/conformance/profiles.json`).
- Gaps: none; every vector of the claimed profiles is replayed, and the `plugin` runner subcommand passes.
- Maturity: Experimental until there is a release pinned to a spec tag.
